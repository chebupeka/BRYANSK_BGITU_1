# Документ за 3 шага

Основной каркас проекта для передачи команде: черновик → тип документа и реквизиты → скачиваемый DOCX. Работает локально без ключей API и внешних сервисов.

**По умолчанию включена заглушка, а не готовый конкурсный MVP.** В режиме `stub` обработчик сохраняет непустые строки исходника без изменения слов и фактов. Режим `llm` подключает локальную модель через Ollama: она исправляет орфографию и приводит текст к деловому стилю, а сервис сверяет её ответ с черновиком и не пропускает выдуманные даты, суммы и имена. Интерфейс сообщает, какой режим включён.

## Что работает

- React + TypeScript + Vite, компоненты Ant Design и три этапа работы.
- Четыре типа: служебная записка, докладная записка, информационная справка и письмо.
- Два оформления: «Классический» и «Компактный» с разными шрифтами, полями, интервалами и выравниванием.
- Формы реквизитов из YAML. Вместо недостающих обязательных значений — `[Заполнить: название поля]`; необязательные пустые поля пропускаются.
- Реквизиты подставляются из черновика на втором шаге и не повторяются в тексте документа. Берутся подписанные строки («Кому: директору», «Тема — закупка») и записи, которые толкуются однозначно: «Исх. № 12-45 от 11.09.2026» разделяется на номер и дату, дата отдельной строкой считается датой документа, «Приложение на 2 листах» уходит в приложение. Адресата и подписанта из обычного текста не выводим: пустое поле честнее выдуманного.
- Реквизиты привязаны к черновику. Изменили текст — прежние значения стираются, и поля заполняются заново по новому черновику.
- Редактируемые абзацы DOCX через python-docx. Дата, номер и подписант автоматически не придумываются.
- localStorage для черновика, выбранного оформления и реквизитов каждого типа. При ошибке данные остаются в форме, доступна повторная попытка.
- Смена оформления использует уже подготовленное содержание и не вызывает обработчик повторно. Изменение текста, типа или реквизитов сбрасывает подготовленный результат.
- Режим `llm`: локальная модель через OpenAI-совместимый API Ollama, строгий JSON-ответ, один повтор при нарушении схемы или новых фактах, обнуление неподтверждённых реквизитов и предупреждения в интерфейсе.
- FastAPI/OpenAPI, проверки Pydantic, API-тесты и GitHub Actions.

Конфигурации реквизитов и оформления — стартовые. Их нужно сверить с эталонами организаторов: отдельного комплекта таких эталонов в переданных материалах не было. Соответствие конкретному ГОСТ или стандарту организации не заявляется.

## Быстрый запуск через Docker

Нужен запущенный Docker Engine с Compose. Из корня репозитория:

```sh
docker compose up --build
```

- Интерфейс: [localhost:8080](http://localhost:8080).
- Документация API: [localhost:8000/docs](http://localhost:8000/docs).
- Проверка сервера: [localhost:8000/api/health](http://localhost:8000/api/health).

`.env` необязателен для первого запуска; по умолчанию используется `TEXT_PROCESSOR=stub`. Порты привязаны к локальному компьютеру. Остановка: `docker compose down`.

### Если сборка прервалась на скачивании Python-пакетов

`ReadTimeoutError` для `files.pythonhosted.org` означает, что pip не дождался данных при загрузке зависимости. Обновите репозиторий и повторите обычную сборку:

```sh
git pull --ff-only
docker compose up --build
```

В backend-образе установлен pip 26.2.1: время ожидания сетевых операций — 120 секунд, до пяти повторов соединения и до пяти попыток продолжить незавершённую загрузку. Обновление старого pip из базового образа повторяется до трёх раз. [Параметры pip](https://pip.pypa.io/en/stable/cli/pip/) применяются и при сборке самого приложения. Загруженные пакеты сохраняются в кэше BuildKit между сборками; кэш не включается в итоговый образ. Для повторной попытки не нужны `--no-cache` или очистка Docker.

После запуска можно проверить путь через nginx до скачивания DOCX командой `python scripts/check_docker.py` (только стандартная библиотека Python). Если скачивания продолжают обрываться после повторов, проверьте доступ Docker к `pypi.org` и `files.pythonhosted.org`, в том числе настройки прокси/VPN.

## Локальная разработка

Нужны Python 3.12–3.14 и Node.js 22.12+; в CI используются Python 3.12 и Node.js 24. Зависимости зафиксированы в lock-файлах. Актуальные руководства: [Vite](https://vite.dev/guide/), [FastAPI](https://fastapi.tiangolo.com/tutorial/), [python-docx](https://python-docx.readthedocs.io/en/latest/).

Клонирование:

```sh
git clone https://github.com/chebupeka/BRYANSK_BGITU_1.git
cd BRYANSK_BGITU_1
```

Первый терминал, PowerShell:

```powershell
Copy-Item .env.example .env
cd backend
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.lock
.venv/Scripts/python.exe -m pip install --no-deps -e .
.venv/Scripts/python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Для Linux/macOS:

```sh
cp .env.example .env
cd backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.lock
.venv/bin/python -m pip install --no-deps -e .
.venv/bin/python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Второй терминал, из корня репозитория:

```sh
cd frontend
npm ci
npm run dev
```

Откройте [localhost:5173](http://localhost:5173). Vite перенаправляет `/api` на порт 8000; в Docker это делает nginx. CORS для обычного запуска не нужен. Если PowerShell блокирует `npm.ps1`, используйте `npm.cmd` вместо `npm`.

Для проверки production-сборки: `npm run build`, затем `npm run preview` из `frontend`. API должен продолжать работать; интерфейс будет на [localhost:4173](http://localhost:4173).

## Конфигурация

Скопируйте корневой `.env.example` в `.env`. После изменения перезапустите backend; для Compose выполните `docker compose up -d --force-recreate` (оба сервиса, чтобы nginx обновил адрес backend).

| Переменная | Сейчас |
| --- | --- |
| `TEXT_PROCESSOR=stub` | Перенос текста без исправлений, режим по умолчанию |
| `TEXT_PROCESSOR=unavailable` | Ответ 503 при подготовке документа; режим проверки ошибки |
| `TEXT_PROCESSOR=llm` | Исправление текста локальной моделью через Ollama |
| `LLM_BASE_URL` | Адрес OpenAI-совместимого API, по умолчанию `http://localhost:11434/v1` |
| `LLM_MODEL` | Имя модели, например `qwen2.5:7b-instruct`; обязательно при режиме `llm` |
| `LLM_API_KEY` | Ollama его не проверяет, нужен другим совместимым серверам; не коммитить |
| `LLM_TIMEOUT_SECONDS` | Ожидание ответа модели, по умолчанию 120 |

ИИ включается только при `TEXT_PROCESSOR=llm`: в остальных режимах обработчик не делает сетевых вызовов. Черновик уходит по адресу из `LLM_BASE_URL` — с локальной Ollama он не покидает компьютер. Базы данных и серверного хранения черновиков нет, файлы создаются в памяти на время запроса. localStorage сохраняет данные на текущем устройстве до очистки данных сайта; подготовленный результат после перезагрузки нужно получить заново.

## Подключение Ollama

Режим `llm` работает с любым OpenAI-совместимым сервером, который поддерживает `response_format: json_object`. Проверялся с [Ollama](https://ollama.com/download).

Ollama на своём компьютере:

```sh
ollama pull qwen2.5:7b-instruct
ollama serve
```

В `.env`: `TEXT_PROCESSOR=llm`, `LLM_BASE_URL=http://localhost:11434/v1`, `LLM_MODEL=qwen2.5:7b-instruct`. Перезапустите backend. Если backend работает в Docker, а Ollama — на хосте, укажите `LLM_BASE_URL=http://host.docker.internal:11434/v1`.

Ollama внутри Compose (профиль `llm` не входит в обычный запуск; образ и веса скачиваются отдельно):

```sh
docker compose --profile llm up -d
docker compose --profile llm exec ollama ollama pull qwen2.5:7b-instruct
docker compose up -d --force-recreate backend
```

Тогда в `.env` достаточно `TEXT_PROCESSOR=llm` и `LLM_MODEL=qwen2.5:7b-instruct`: адрес `http://ollama:11434/v1` подставится сам. Проверка: в `GET /api/health` поле `processor_mode` должно быть `llm`. Если модель недоступна, подготовка вернёт 503 с понятным текстом, а черновик останется в форме.

### Ollama на другом компьютере

Модель может стоять на машине посильнее, а сервис работать на вашей. Веса нужны только там, где запущена Ollama. Ниже — случай общей сети. Если компьютеры в разных сетях, смотрите [гайд по подключению машины из другой сети](docs/REMOTE_MODEL.md): он написан так, чтобы её владелец настроил всё сам, без вашего участия.

На компьютере с моделью Ollama по умолчанию слушает `127.0.0.1`, поэтому её надо открыть в сеть и перезапустить:

```sh
launchctl setenv OLLAMA_HOST 0.0.0.0     # macOS, затем перезапустить приложение Ollama
sudo systemctl edit ollama               # Linux: Environment="OLLAMA_HOST=0.0.0.0", потом restart
setx OLLAMA_HOST 0.0.0.0                 # Windows, затем перезапустить Ollama
```

Узнайте адрес этой машины (`ipconfig getifaddr en0` на macOS, `hostname -I` на Linux) и укажите его в `.env` там, где работает сервис:

```sh
LLM_BASE_URL=http://192.168.1.25:11434/v1
```

Связь проверяется до запуска: `python scripts/check_llm.py http://192.168.1.25:11434/v1` покажет список моделей на сервере и прогонит один черновик, проверив, что ответ приходит строгим JSON и факты в нём сохранены. Без аргументов скрипт берёт адрес и модель из `.env`. Разрешите Ollama входящие подключения, если брандмауэр спросит.

Открытый порт 11434 не требует пароля: любой в той же сети сможет пользоваться моделью, а черновики пойдут по сети в открытом виде. `LLM_API_KEY` тут не поможет, Ollama ключи не проверяет. На конкурсном Wi-Fi надёжнее тоннель SSH: Ollama остаётся на `127.0.0.1`, трафик шифруется, вход по учётной записи.

```sh
ssh -N -L 11435:localhost:11434 пользователь@192.168.1.25
```

Локальный порт взят другой, потому что 11434 может быть занят своей Ollama. Тогда в `.env` укажите `LLM_BASE_URL=http://localhost:11435/v1`.

Модель выбирает команда. Чем меньше модель, тем чаще она нарушает схему и попадает под повтор; на слабой машине запуск занимает десятки секунд, поэтому интерфейс ждёт подготовку до 4 минут.

Окно модели важнее её размера. Ollama по умолчанию держит окно в 4096 токенов, даже если модель умеет больше, и молча отбрасывает то, что не поместилось: без защиты начало длинного черновика просто исчезает. Сервис режет такой черновик на части и обрабатывает их по очереди, поэтому текст не теряется, но каждая часть — отдельный запрос. Черновик на 8000 символов занимает около четырёх минут. Чтобы частей было меньше, поднимите окно на сервере модели (`OLLAMA_CONTEXT_LENGTH=16384`) и согласуйте с ним `MODEL_CONTEXT_TOKENS` в `backend/app/processing.py`.

Что сервис делает с ответом модели:

1. Из черновика и ответов пользователя независимо извлекаются даты, числа и имена.
2. Модель отвечает строго JSON: `requisites`, `body`, `changes`; форма ответа проверяется Pydantic.
3. Нарушение схемы или новые факты дают ровно один повтор с указанием причины.
4. После повтора неподтверждённый реквизит обнуляется и попадает в «не заполнено», а неподтверждённые сведения в тексте помечаются предупреждением, а не удаляются молча.
5. Сверка идёт и в обратную сторону: если число или дата из черновика в документ не попали, появляется предупреждение о потере.
6. Отдельно проверяются условия и отрицания: «если», «только», «не позднее», «не». Если оговорка из черновика исчезла, появляется предупреждение о смысле, а не о фактах.
7. Сумма прописью и цифрами считается одним сведением, фамилия в другом падеже — тем же лицом. Тему документа обработчик формулирует сам, остальные реквизиты берёт только там, где они названы прямо.
8. Ответы пользователя всегда важнее значений, предложенных моделью.
9. Последние 16 подготовок держатся в памяти: тот же черновик с теми же ответами возвращается мгновенно, а смена оформления обработчик не трогает вовсе.

## Структура

```text
backend/
  app/
    main.py              # маршруты API и сборка приложения
    schemas.py           # контракты Pydantic
    settings.py          # переменные окружения
    processing.py        # граница TextProcessor, заглушки и адаптер модели со сверкой фактов
    extraction.py        # разбор подписанных строк черновика в реквизиты
    catalog.py           # загрузка и проверка конфигураций
    docx_generator.py    # «структура типа × оформление шаблона»
    doc_types/*.yaml     # реквизиты и порядок блоков четырёх типов
    templates/*.yaml     # параметры двух оформлений
  tests/                 # содержательные проверки API и DOCX
frontend/
  src/
    App.tsx              # переходы, состояние и обработка ошибок
    api.ts               # единственная точка HTTP-вызовов
    storage.ts           # восстановление и сохранение черновика
    types.ts             # типы API для интерфейса
    components/          # настройки и просмотр содержания
docs/                    # архитектура, API и задачи команды
examples/                # явно демонстрационные входные данные
compose.yaml
.github/workflows/checks.yml
```

## Отчёт о качестве

Качество обработки меряется одним набором черновиков, чтобы правки промпта и смена модели сравнивались числом, а не ощущением. Нужна запущенная модель:

```sh
backend/.venv/bin/python scripts/quality_report.py
backend/.venv/bin/python scripts/quality_report.py --model qwen2.5:14b-instruct --json отчёт.json
```

Случаи лежат в `examples/quality_cases.yaml`: черновик, тип документа и проверки к результату. Проверяется, что сведения дошли до документа, названные опечатки исправлены, запрещённые обороты не появились, реквизиты заполнены там, где их можно взять из текста, и не выдуманы там, где их нет. Сравнение сведений берётся из самого обработчика, поэтому «30 000» и «тридцать тысяч» считаются одним и тем же. Набор стоит пополнять: каждый новый случай ловит то, что иначе всплывёт на защите.

## Проверки

Из `backend` на Windows:

```powershell
.venv/Scripts/python.exe -m ruff check .
.venv/Scripts/python.exe -m pytest -q
```

На Linux/macOS замените `.venv/Scripts/python.exe` на `.venv/bin/python`. Из `frontend`: `npm run build` (включает проверку TypeScript). Те же проверки выполняет GitHub Actions.

Тесты проверяют восемь сочетаний типа и шаблона, сохранение исходных фактов, метки пропусков, введённые реквизиты, отличие оформления без изменения текста, некорректные запросы и отказ обработки. Отдельный набор проверяет режим `llm` на расписанных ответах модели: приоритет ответов пользователя, обнуление неподтверждённого реквизита, один повтор, явную ошибку после повтора, сетевой сбой и сведение дат и сумм к одному виду. Запущенная Ollama для тестов не нужна. Это структурная проверка DOCX; визуальный вид в Word/LibreOffice проверяется отдельно по [сценариям](docs/HANDOFF.md#проверка-перед-передачей).

### Попробовать вручную

1. Нажмите «Вставить пример» или используйте вход из `examples/service_memo.json`. Это вымышленные демонстрационные данные.
2. Выберите тип и оформление, заполните реквизиты либо оставьте часть пустой.
3. Подготовьте и скачайте DOCX. Убедитесь, что метки пропусков видны, а текст редактируется.
4. Вернитесь к реквизитам, смените только оформление, скачайте второй файл: содержание совпадёт.
5. Установите `TEXT_PROCESSOR=unavailable`, перезапустите backend и попробуйте подготовить изменённый черновик. Должна появиться ошибка. Верните `stub`, перезапустите backend и нажмите «Повторить подготовку».
6. Для проверки ИИ включите `TEXT_PROCESSOR=llm` с запущенной Ollama и подготовьте `examples/typos.txt`: текст должен стать грамотным, а даты, суммы и имена — остаться прежними.

## Продолжение работы

Для первого прохода команде достаточно прочитать [архитектуру и API](docs/ARCHITECTURE.md), затем [распределение задач и сценарии проверки](docs/HANDOFF.md). Исходный краткий контекст сохранён в [docs/CONTEXT.md](docs/CONTEXT.md).

Добавление типа: создайте `backend/app/doc_types/*.yaml` с уникальным `id`, `name`, `description`, `title`, `fields` и `blocks`. Необязательный `summary: true` у реквизита разрешает обработчику сформулировать значение по смыслу черновика: так помечена только тема документа, остальные поля заполняются лишь по прямому упоминанию. Каждый реквизит, а также `title` и `body` должны присутствовать в `blocks` ровно один раз. Перезапустите backend; форма и генератор подхватят новый тип из каталога. Содержательные правила заполнения нового типа реализуются отдельно в обработчике.

Добавление оформления: скопируйте YAML из `backend/app/templates`, задайте уникальный `id` и измените оформление. Параметры валидируются при запуске. Текст и набор реквизитов в шаблон не помещаются. Новые способы расположения блоков или колонтитулы потребуют расширить контракт Template и генератор.

LLM-адаптер за `TextProcessor` реализован: строгая JSON-схема, независимое извлечение и сверка фактов, не более одного повтора при неверном ответе. Осталось: сверка конфигураций с эталонами организаторов и проверка качества на длинных документах.

Ограничения: нет авторизации, серверной истории, кэша, переживающего перезапуск, редактирования результата в интерфейсе и защиты для публичного многопользовательского размещения. До такого размещения команда должна выбрать правила доступа, ограничения запросов и хранения документов. Пока проект предназначен для локальной разработки и демонстрации.
