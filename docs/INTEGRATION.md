## Последовательность

1. **Принять основу роли 1.** Проверить backend, экспорт контрактов, сборку frontend и Compose в `stub`, затем объединить `feat/role-1-backend-integration` через отдельный PR. Участники обновляют свои ветки от принятой основы. Не заменять новые `main.py`, `settings.py` и контракт ошибок старыми файлами целиком.
2. **Подключить DOCX.** Внести `feature/docx-configs` вместе с дополнениями схемы и каталога. Сохранить сигнатуру renderer `(content, doc_type, template) -> bytes`. Проверить 4 типа × 2 оформления, затем заново экспортировать контракты и собрать frontend. Просмотр страниц DOCX провести отдельно.
3. **Подключить QA и привести проверки к согласованному DOCX-контракту.** Корпус и независимый эталон сохраняются. Исправить перечисленные ниже предположения о заголовках, подписях полей и пробелах; прогнать все офлайн-тесты. При изменении обязательности реквизитов пересмотреть манифест вместе с ролью 3.
4. **Подключить содержательную обработку роли 2.** Адаптацию `feature/ollama-text-processor` можно готовить параллельно, но объединять после проверки общего интерфейса. Использовать `create_app(content_policy=...)` для штатного транспорта либо `create_app(processor=...)` для полной замены. Согласовать `openai`/`llm`, не запускать вложенные повторы и не оставлять два независимых транспорта одного режима.
5. **Выполнить общий приёмочный прогон.** Повторить API/контракты/frontend/Compose, затем явно включить согласованные проверки настоящей модели и проверить документы в Word/LibreOffice. Результаты на `stub` не считать доказательством исправления текста моделью.

Каждый шаг — отдельное проверяемое изменение. Текстовые конфликты разрешаются по ответственности выше, а успешный merge подтверждается тестами поведения. Если ветки уже объединяются в другом порядке, те же контрольные точки обязательны.

## DOCX: что сохранить при объединении

Ветка DOCX добавляет `Placement`, поля `RequisiteField.placement/prefix`, `DocumentType.show_title` и параметры `Template`: `letterhead_alignment`, `headline_alignment`, `headline_bold`, `addressee_width_mm`, `small_font_size`, `page_numbers`. Эти дополнения нужно сохранить **вместе** с `HealthResponse`, `ReadyResponse`, `ErrorResponse` и остальными схемами роли 1. После объединения `schemas.py` обязательно перегенерировать OpenAPI и TypeScript.

Новые YAML-файлы нельзя переносить отдельно от схемы и каталога: общий контракт запрещает неизвестные поля, а обновлённый каталог дополнительно проверяет соседство сгруппированных реквизитов и ширину адресного блока. Новые поля необязательны по умолчанию; идентификаторы типов и шаблонов сохранены (`classic` и `modern`). Старые корректные запросы должны продолжать приниматься — это нужно подтвердить повторным прогоном [api.http](../examples/api.http).

`README.md`, `docs/ARCHITECTURE.md` и `docs/HANDOFF.md` изменены и ролью 1, и DOCX-веткой. При разрешении конфликтов сохранить актуальные запуск, LLM-настройки, кэш, ошибки и точки подключения; добавить фактические особенности нового renderer. Не возвращать прежние утверждения, что LLM-переменные не используются или кэша нет.

## QA: конкретные несовпадения с DOCX

| Место | Найденное несовпадение | Как разрешить |
| --- | --- | --- |
| `test_scenarios.py`: структура каждого типа | Тест требует заголовок типа всегда, DOCX задаёт `show_title: false` для письма | Проверять наличие/отсутствие заголовка по согласованному `show_title`; оставить проверку структуры письма |
| `test_docx_conformance.py`: порядок реквизитов | Тест ищет отдельные абзацы `label: value`; DOCX объединяет дату/номер, ссылки и подпись, многие подписи полей не печатает | Искать значения и группы по `placement`, учитывать несколько реквизитов в одном абзаце; не ослаблять проверку полноты и порядка |
| `qa_support.body_paragraphs`, проверки типографики и прямого совпадения текста | DOCX заменяет пробел в `№ 214` и `30 000` на U+00A0; буквальное сравнение может не найти текст | Для сравнения содержания нормализовать только согласованные типографские пробелы; отдельно проверять наличие нужных неразрывных пробелов |
| `qa_support.keeps` | Нормализация уже учитывает разряды чисел, но не всякое различие пробела после `№` | Дополнить нормализацию для типографски равнозначных пробелов, сохраняя проверку самих значений |
| Манифест корпуса и обязательные поля | QA проверяет, что `not_in_draft` содержит только обязательные реквизиты | После согласованного изменения обязательности проверить все случаи манифеста, не подставлять вымышленные значения |
| `test_llm_scenarios.py` | Gate, создание Settings и ожидаемый результат жёстко используют `llm`; основа роли 1 использует `openai` | Согласовать имя/alias и обновить все три места. Иначе даже `QA_LLM=1` пропустит тесты |
| Проверка «модель переписала текст» | Штатная `PreserveSourcePolicy` намеренно запрещает переписывание | В приёмочном наборе создавать приложение с настоящей политикой роли 2; тесты сохранения исходника оставить для штатного режима |

Ветви QA и DOCX меняют разные тестовые файлы, поэтому эти несовпадения могут пройти обычное объединение Git без конфликтов. Их исправление — часть интеграции, не причина удалить тесты.

## ИИ-ветка: адаптер и настройки

У `feature/ollama-text-processor` HTTP-пути и основная форма запросов/ответов сохранены, но внутренний интерфейс отличается. Ветка использует `process(request, doc_type)`, атрибут `mode='llm'` и результат без обязательного `processor_mode`. Основа роли 1 ожидает `process(request)`, `close()` и `ProcessorResult(document, changes, warnings, processor_mode)`.

Для первого объединения перенесите реализацию ИИ и её функции фактов в отдельный модуль роли 2, затем подключите полный processor через адаптер:

1. Адаптер получает `doc_type` из `document_types()[request.doc_type]` и вызывает существующий `process(request, doc_type)` участника 2.
2. Преобразует ответ в общий `app.processing.ProcessorResult`, явно задавая согласованный `processor_mode`.
3. Преобразует исключения в общий `ProcessorUnavailable` с безопасным сообщением, кодом, HTTP-статусом и признаком повтора. Не отдаёт клиенту текст ошибки провайдера из старого `server_error_text`.
4. Предоставляет `close()`. При передаче готового процессора через `create_app(processor=...)` закрытие внешних ресурсов остаётся обязанностью кода, создавшего его.
5. Переносит внутренние тесты роли 2 на импорт её отдельного модуля, а проверки HTTP проводит через адаптер.

Прямая подмена `app.processing` сломает сборку роли 1. Немедленная замена одним `ContentPolicy` тоже требует доработки: промпт ИИ-ветки строится через `build_messages(request, doc_type, answered)`, а предупреждения зависят от запроса; текущие `system_prompt()` и `warnings()` политики не принимают эти аргументы. Полный адаптер сохраняет эти возможности, дальнейшее выделение общей политики можно выполнить отдельным изменением.

ИИ-ветка также добавляет `RequisiteField.summary` и `summary: true` для `subject` во всех четырёх YAML. Это поле нужно объединить с DOCX-полями `placement/prefix`, а не выбрать только один набор. Без `summary` в строгой Pydantic-схеме перенос её YAML приведёт к ошибке загрузки каталога. Затем обновить TypeScript/OpenAPI.

| Настройка | ИИ-ветка | Основа роли 1 | Действие при интеграции |
| --- | --- | --- | --- |
| Режим | `llm` | `openai` | Выбрать единое имя либо явно реализовать alias; обновить Settings, UI, QA и примеры вместе |
| Таймаут LLM | 120 s | 20 s, допустимо до 60 s | Согласовать с верхними пределами backend, frontend и nginx; не переносить только `.env` |
| Профиль Compose | `llm` | `ollama` | Оставить одно имя и исправить команды документации |
| Volume модели | `ollama-models` | `ollama_models` | Сохранить выбранный volume или явно перенести модели; смена имени создаст отдельное хранилище |
| Порт Ollama | Публикуется 11434 | Только сеть Compose | Выбрать способ доступа и соответствующий `LLM_BASE_URL` |

Назначение Python-зависимости `httpx` совпадает: в обеих реализациях она нужна приложению, а не только тестам. Сохраните её в production-зависимостях и согласуйте оба lock-файла.

Есть отдельное содержательное расхождение: тест ИИ-ветки `test_invented_fact_after_retry_is_flagged_but_document_returned` ожидает успешный документ с новым значением после двух попыток и предупреждением. Потеря части фактов тоже может завершаться предупреждением. Это не эквивалент штатной политике роли 1 и не подтверждает запрет выдуманных фактов. До приёмки роль 2 должна определить и проверить поведение: неподтверждённое содержание не должно становиться обычным успешным документом только из-за исчерпания повторов. Адаптер сам по себе эту проблему не решает.

## Эталон кейса и оформление

В QA-ветке `examples/reference/case_reference.yaml` — отдельный эталон, а не текущая конфигурация сервиса. Он расходится с DOCX-веткой: например, номера записок в нём обязательные, в DOCX — необязательные; у оформления `modern` в эталоне 12 pt и поля 15/20/15/25 мм, в DOCX — 11 pt и по 25 мм. Также различаются ожидаемые колонтитулы и расположение подписи.

Эти расхождения нельзя исправить выбором целого файла `ours`/`theirs`. Роли 3 и 5 должны сверить требования исходного кейса и зафиксировать выбранные правила. Заявление о стандарте в названии коммита DOCX само по себе не доказывает соответствие эталону кейса; этот документ не оценивает такое соответствие.

Отчёт QA сейчас ищет ключ `header` в каталоге, а DOCX-ветка задаёт `page_numbers` и добавляет поле PAGE. Поэтому сообщение «колонтитулы не заданы» после интеграции не будет точным описанием файла. Проверку следует расширить: различать отсутствие колонтитула и несоответствие нужному содержанию/расположению. Сам отчёт завершает работу с кодом 0 при расхождениях с эталоном, если корпус проходит; нулевой код не равен отсутствию всех замечаний.

## Проверки после каждого шага

Из корня, после установки зависимостей по [README](../README.md):

```powershell
backend/.venv/Scripts/python.exe -X utf8 -m pytest backend/tests -q
backend/.venv/Scripts/python.exe -m ruff check backend
backend/.venv/Scripts/python.exe scripts/export_contracts.py
backend/.venv/Scripts/python.exe scripts/export_contracts.py --check
npm --prefix frontend run build
```

После подключения QA отчёт использует обычный `Settings()` и не защищён флагом `QA_LLM`. Для офлайн-прогона явно выбирайте `stub`, иначе при настроенном `openai` отчёт обратится к провайдеру:

```powershell
$env:TEXT_PROCESSOR = 'stub'
backend/.venv/Scripts/python.exe -X utf8 scripts/qa_report.py --out qa_samples
```

Это переключение действует в текущем терминале. После прогона верните нужный режим либо закройте терминал. Для проверки Compose используйте `python scripts/check_docker.py`; он сам отказывается обращаться к настоящей модели. Для реальной модели запуск должен быть отдельным и осознанным, с правильно подключённой политикой и актуальным gate QA.

На текущей основе роли 1 все девять запросов из `examples/api.http` проверены через FastAPI TestClient: успешные запросы, оба DOCX-архива, ошибки 422/503, Request ID, кэш MISS/HIT и readiness отказа. Это проверка текущего backend; объединённые удалённые ветки таким прогоном пока не проверены.
