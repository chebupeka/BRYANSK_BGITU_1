# Контекст проекта: «Документ за 3 шага»

Нужно создать конкурсный MVP веб-сервиса: пользователь вводит черновик, выбирает тип документа и шаблон, получает редактируемый DOCX.

## Обязательный пользовательский путь
1. Ввод или вставка черновика с возможностью отредактировать до обработки.
2. Выбор одного из типов: служебная записка, докладная записка, информационная справка, письмо.
3. Выбор одного из минимум двух визуально разных шаблонов.
4. ИИ исправляет орфографию и приводит текст к официально-деловому стилю.
5. Сервис проверяет обязательные реквизиты, запрашивает их либо оставляет `[Заполнить: поле]`.
6. Генерируется скачиваемый DOCX с редактируемым текстом.

## Непереговорные правила
- Нельзя выдумывать факты, даты, суммы, ФИО, номера или содержательные реквизиты.
- Изменение типа меняет структуру и обязательные поля; изменение шаблона меняет только оформление.
- Оформление задаётся программно, а не ответом модели.
- При сбое LLM черновик сохраняется, показывается понятная ошибка и доступна повторная попытка.
- Веб-интерфейс должен работать на ширине от 320 px.

## Рекомендуемый стек
- Frontend: React + Vite + Ant Design (Steps), localStorage для черновика.
- Backend: Python + FastAPI + Pydantic; хранение в памяти/файлах достаточно.
- DOCX: python-docx; шаблоны и типы в YAML-конфигурациях.
- LLM через OpenAI-совместимый API: `LLM_BASE_URL`, `LLM_MODEL` в `.env`.
- Docker Compose: frontend, backend, LLM (опционально), LanguageTool (опционально).

## Конвейер обработки
`черновик → извлечение фактов → LLM JSON → Pydantic → сверка фактов → реквизиты → DOCX`.
LLM возвращает строго JSON: `requisites`, `body` (абзацы), `changes`.
Непустые реквизиты и факты результата должны подтверждаться исходником или ответом пользователя; иначе обнуляются/помечаются.
Повторный вызов LLM допустим один раз при нарушении схемы или появлении неподтверждённых фактов.

## Структура данных
- `doc_types/*.yaml`: обязательные реквизиты, порядок блоков, правила для 4 типов.
- `templates/*.yaml` и/или базовые `.docx`: поля, шрифт, интервалы, отступы, колонтитулы, расположение блоков.
- Генератор соединяет «структура типа × оформление шаблона».
- Кэш LLM: hash(черновик, тип, ответы пользователя); смена шаблона не вызывает LLM повторно.

## Приоритет реализации
1. Сквозной путь для одной служебной записки в двух шаблонах, допустима заглушка LLM.
2. Все четыре типа, форма недостающих реквизитов, DOCX и fallback при ошибке.
3. Фактчекинг, тесты сценариев 1-6, README, архитектурная схема, демо-данные.
4. Если осталось время: предпросмотр и ручное редактирование результата, история, сравнение изменений.

## Команда из 6
1. API, Docker, API-контракты и интеграция LLM.
2. Промпт, JSON-схемы, извлечение/сверка фактов.
3. DOCX-генератор, 4 типа и 2 шаблона.
4. React-интерфейс, адаптивность, состояния и ошибки.
5. Тестовые черновики, автотесты и проверка DOCX.
6. README, архитектурная схема, демонстрация и презентация до 7 минут.

## Критерии готовности
Эксперт без помощи команды проходит сценарии: полный путь, исправление ошибок без искажения смысла, пропущенные реквизиты, все типы, смена шаблонов и отказ LLM.
Репозиторий содержит команды запуска, `.env.example`, демо-входы, описание архитектуры, ограничений и добавления нового типа/шаблона.
