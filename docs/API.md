# API для команды

Адрес при разработке: `http://localhost:8000`. Через Docker frontend API доступен и по `http://localhost:8080/api/...`. JSON передавайте с `Content-Type: application/json`.

Интерактивная документация — `/docs`, текущая схема — `/openapi.json`. Зафиксированные контракты: [OpenAPI](../contracts/openapi.json), [TypeScript](../contracts/api.ts), [ответ модели](../contracts/llm-output.schema.json). Готовые запросы: [examples/api.http](../examples/api.http).

## Маршруты

| Метод и путь | Успех | Назначение |
| --- | --- | --- |
| `GET /api/health` | `200 HealthResponse` | Проверка жизни API, без обращения к LLM |
| `GET /api/ready` | `200 ReadyResponse` | Готовность локальной конфигурации, при отказе `503` |
| `GET /api/catalog` | `200 Catalog` | Типы, реквизиты, оформления и режим обработчика |
| `POST /api/requisites/suggest` | `200 RequisiteSuggestions` | Черновик и тип → реквизиты, подписанные в черновике прямо; модель не участвует |
| `POST /api/process` | `200 ProcessResponse` | Черновик и реквизиты → подготовленное содержание |
| `POST /api/documents/download` | `200`, бинарный DOCX | Содержание + оформление → файл, без LLM |

### Health и readiness

`GET /api/health`:

```json
{"status": "ok", "processor_mode": "stub"}
```

`GET /api/ready`:

```json
{
  "status": "ready",
  "processor_mode": "stub",
  "checks": {"catalog": true, "processor": true}
}
```

В `unavailable` readiness отвечает `503`. В `openai` и `llm` незаданная модель также даёт `503`. Успешный readiness не доказывает доступность провайдера: он не делает сетевой или платный запрос. Для проверки реального LLM выполните `/api/process`.

### Каталог

`Catalog` содержит `doc_types`, `templates`, `processor_mode`. Поля выбранного типа перечислены в `doc_types[].fields`: `id`, `label`, `required`. Стройте форму по каталогу; не отправляйте реквизиты другого типа.

Сейчас доступны `service_memo`, `report_memo`, `information_note`, `letter`; оформления — `classic` («Классический») и `modern` («Компактный»). Новые записи YAML появятся после перезапуска.

### Подготовка

`POST /api/process`:

```json
{
  "doc_type": "service_memo",
  "draft": "Прошу согласовать закупку двух мониторов.",
  "requisites": {"subject": "О закупке мониторов"}
}
```

Ответ в режиме `stub`:

```json
{
  "document": {
    "doc_type": "service_memo",
    "requisites": {"subject": "О закупке мониторов"},
    "body": ["Прошу согласовать закупку двух мониторов."]
  },
  "missing_fields": [
    {"id": "recipient", "label": "Кому", "required": true},
    {"id": "sender", "label": "От кого", "required": true},
    {"id": "date", "label": "Дата", "required": true},
    {"id": "signer", "label": "Подписант", "required": true}
  ],
  "changes": [],
  "warnings": [
    "Демонстрационный режим: текст перенесён без исправлений. Проверка орфографии и делового стиля пока не подключена."
  ],
  "processor_mode": "stub"
}
```

Текст предупреждений может меняться; не используйте его как машинный код режима. `missing_fields` содержит только незаполненные обязательные реквизиты. Пользователь может заполнить их и повторить подготовку либо скачать документ с метками пропусков. `changes` и `warnings` принадлежат результату обработки, оформление в запрос не входит.

### Скачивание

Передайте `document` из успешной обработки:

```json
{
  "document": {
    "doc_type": "service_memo",
    "requisites": {"subject": "О закупке мониторов"},
    "body": ["Прошу согласовать закупку двух мониторов."]
  },
  "template_id": "classic"
}
```

Ответ имеет media type `application/vnd.openxmlformats-officedocument.wordprocessingml.document` и `Content-Disposition: attachment; filename="service_memo-classic.docx"`. Читайте тело как бинарные данные, например `response.blob()`, а не JSON. Отдельного URL файла и серверной сессии нет.

Для второго оформления отправьте тот же `document` с `template_id=modern`. Обработка и доступность LLM не требуются. Скачивание принимает документ напрямую, поэтому не является удостоверением прохождения фактчекинга.

## Ограничения данных

- Неизвестные свойства JSON запрещены.
- `draft`: 1–20 000 символов; одни пробелы не допускаются.
- `requisites`: до 30 полей, значение каждого — до 500 символов; крайние пробелы значения убираются.
- `body`: непустой массив непустых строк, до 10 000 абзацев; суммарный текст — до 20 000 символов и не только пробельные символы.
- Идентификатор: первая буква `a–z`, далее `a–z`, цифры или `_`, всего до 50 символов. Он также должен существовать в соответствующем каталоге.
- Управляющие символы, недопустимые в XML 1.0, отклоняются до генерации DOCX.

Pydantic выполняет и проверки, которые не выражаются полностью в JSON Schema, например суммарную длину `body`. Окончательная проверка остаётся на backend.

## Заголовки и кэш

`X-Request-ID` возвращается в ответе API. Клиент может прислать свой идентификатор; если он не подходит серверу, backend создаст новый. При ошибке используйте идентификатор из ответа для диагностики.

Успешный `/api/process` возвращает `X-Cache`:

| Значение | Значение для клиента |
| --- | --- |
| `MISS` | Успешно выполнена обработка и результат сохранён в кэш |
| `HIT` | Возвращён результат предыдущего такого же запроса |
| `BYPASS` | Кэш отключён |

Ключ зависит от черновика, типа и реквизитов, не от оформления. По умолчанию до 128 результатов живут до 300 секунд в памяти одного процесса. `CACHE_MAX_ENTRIES=0` или `CACHE_TTL_SECONDS=0` отключает кэш. Ошибки не сохраняются; перезапуск очищает кэш. Кэш не объединяет результаты между отдельными репликами.

## Единая ошибка

Все прикладные ошибки, включая валидацию, возвращают `ErrorResponse`. Поле `detail` всегда строка для совместимости с текущим интерфейсом; новые клиенты используют также `error`:

```json
{
  "detail": "Неизвестный тип документа.",
  "error": {
    "code": "unknown_doc_type",
    "message": "Неизвестный тип документа.",
    "retryable": false,
    "request_id": "team-service-memo-1",
    "details": []
  }
}
```

Для `validation_error` список `error.details` содержит объекты `field`, `message`, `type`, без исходного черновика или ключа API. `detail` и `error.message` описывают одну ошибку. `retryable` — подсказка для повторной попытки пользователя, не команда запускать бесконечные автоматические повторы.

| HTTP | Код | `retryable` | Что делать |
| --- | --- | --- | --- |
| `422` | `validation_error` | `false` | Исправить JSON или значения полей |
| `422` | `unknown_doc_type`, `unknown_requisites`, `unknown_template` | `false` | Обновить каталог и исправить выбор/реквизиты |
| `503` | `processor_unavailable` | `true` | Выбран режим отказа или обработчик недоступен; повторить после восстановления |
| `503` | `llm_not_configured` | `false` | Указать модель и необходимые настройки, перезапустить backend |
| `503` | `processor_busy` | `true` | Все слоты заняты; повторить позже |
| `503` | `llm_connection_error` | `true` | Проверить сеть и адрес провайдера, повторить после восстановления |
| `503` | `llm_auth_error` | `false` | Провайдер вернул 401/403; проверить ключ и доступ к модели |
| `503` | `llm_rate_limited` | `true` | Провайдер вернул 429; повторить позже |
| `502` | `llm_upstream_error` | `true` | Провайдер вернул 5xx; повторить после восстановления |
| `502` | `llm_request_rejected` | `false` | Провайдер отклонил запрос; проверить совместимость API и настройки |
| `502` | `llm_invalid_output` | `false` | Ответ не прошёл JSON/схему/политику после разрешённого повтора; проверить модель и политику |
| `502` | `processor_invalid_output` | `false` | Подключённый модуль вернул другой тип документа или реквизиты чужого типа; исправить реализацию процессора |
| `504` | `llm_timeout` | `true` | Проверить скорость провайдера и таймаут, затем повторить |
| `500` | `internal_error` | `false` | Передать `request_id` владельцу backend |
| `404` / `405` | `http_error` | `false` | Проверить путь и HTTP-метод |

Сетевые сбои и HTTP-ошибки LLM не повторяются автоматически. Невалидный JSON, схема или нарушение политики допускают максимум один исправляющий запрос. При повторной неудаче сервер возвращает ошибку, не подменяет её успешным результатом `stub`.

## Изменение контракта

Редактируйте Pydantic-модели, затем выполните из корня с установленными backend-зависимостями:

```powershell
backend/.venv/Scripts/python.exe scripts/export_contracts.py
backend/.venv/Scripts/python.exe scripts/export_contracts.py --check
```

`--check` сообщает о расхождении с сохранёнными контрактами, включая зеркальный `frontend/src/generated/api.ts`. Этот файл нужен внутри Docker-контекста frontend; `frontend/src/types.ts` реэкспортирует его типы и отдельно определяет `DraftState`. Добавляйте обновлённые `contracts/`, зеркало типов, примеры и необходимые изменения клиента в то же изменение. Для Linux/macOS путь к Python — `backend/.venv/bin/python`.
