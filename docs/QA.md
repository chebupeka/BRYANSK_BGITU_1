# Проверка решения

Документ описывает, чем и как проверяется сервис, что уже проверено автоматически,
что остаётся проверить руками и какие расхождения с эталоном кейса найдены.

## Что где лежит

| Что | Где | Зачем |
| --- | --- | --- |
| Корпус «грязных» черновиков | `examples/drafts/*.txt` | 20 входов: 16 из материалов кейса и 4 крайних случая |
| Описание корпуса | `examples/drafts/manifest.yaml` | для каждого входа: что обязано сохраниться и каких реквизитов в нём нет |
| Эталон заказчика | `examples/reference/case_reference.yaml` | независимая копия перечня реквизитов и описания шаблонов |
| Сценарии 1–6 | `backend/tests/test_scenarios.py` | проверка готовности так, как её описывают критерии оценки |
| Прогон всего корпуса | `backend/tests/test_drafts_corpus.py` | те же правила на каждом из 20 черновиков |
| Проверка файла DOCX | `backend/tests/test_docx_conformance.py` | правила шаблона и состав реквизитов внутри готового файла |
| Проверки самих проверок | `backend/tests/test_qa_support.py` | доказывают, что набор ловит подмену фактов и испорченный файл |
| Сценарии на реальной модели | `backend/tests/test_llm_scenarios.py` | по умолчанию пропускаются, включаются через `QA_LLM=1` |
| Общие средства проверки | `backend/tests/qa_support.py` | сравнение фактов, разбор DOCX, загрузка корпуса |
| Отчёт проверки | `scripts/qa_report.py` | человекочитаемая сводка и сверка с эталоном |

## Как запустить

Автотесты (из каталога `backend`, зависимости по README):

```bash
python -X utf8 -m pytest -q
```

Флаг `-X utf8` нужен на Windows: без него русские сообщения об ошибках выводятся
нечитаемыми, и понять причину падения невозможно.

Отчёт и образцы документов для просмотра глазами (из корня репозитория):

```bash
backend/.venv/Scripts/python scripts/qa_report.py --out qa_samples
```

Отчёт печатает результат по каждому черновику и список расхождений с эталоном кейса,
а с ключом `--out` дополнительно сохраняет четыре типа документов в двух шаблонах
и один длинный многостраничный документ.

## Корпус черновиков

По четыре черновика на каждый из четырёх типов документов и четыре крайних случая:

| Вид входа | Что проверяет |
| --- | --- |
| `*_01_structured` | реквизиты размечены, текст уже близок к деловому — эталон для сравнения |
| `*_02_colloquial` | разговорная речь и ошибки: «Здрасьте», «Вообщем», «барахлит», «испортится» |
| `*_03_incomplete` | обязательных реквизитов не хватает — основной вход для сценария 3 |
| `*_04_flat` | сплошной текст без разметки полей, от третьего лица |
| `edge_01_single_line` | одна строка без знаков препинания и заглавных букв |
| `edge_02_typos_and_noise` | опечатки, капс, markdown-разметка, двойные пробелы |
| `edge_03_mixed_alphabets` | кириллица вперемешку с латиницей |
| `edge_04_number_formats` | «1 марта 2025» и «31.03.2025», сумма прописью, проценты через запятую |

Для каждого входа манифест задаёт `must_keep` — значения, которые обязаны дойти до готового
файла, и `not_in_draft` — обязательные реквизиты, которых в черновике нет. Второе важнее:
именно эти поля система не имеет права заполнить сама.

Сравнение значений не зависит от регистра, а пробелы внутри чисел игнорируются,
поэтому «180 000» и «180000» считаются одним значением.

### Как добавить свой черновик

1. Положить файл в `examples/drafts/`.
2. Добавить случай в `manifest.yaml`: `id`, `file`, `doc_type`, `label`, `dirt`,
   `must_keep`, `in_draft`, `not_in_draft`.
3. Запустить `pytest -q`. Набор сам подхватит новый вход, а тест
   `test_manifest_describes_the_draft_truthfully` проверит, что описание не расходится
   с самим черновиком и с конфигурацией типов документов.

## Сценарии готовности

| Сценарий из критериев | Чем проверен |
| --- | --- |
| 1. Полный путь до DOCX | `test_scenario_1_*`: каталог отдаёт 4 типа и 2 шаблона, черновик доходит до открываемого файла с заголовком типа |
| 2 и 4. Обработка текста и сохранение смысла | `test_scenario_2_and_4_*` и весь `test_drafts_corpus.py`: факты доходят до файла, новых чисел не появляется, результат сообщает, что было сделано |
| 3. Недостающие реквизиты | `test_scenario_3_*`: пропуск найден, поле осталось пустым, в файле стоит метка `[Заполнить: …]`, введённое значение попадает в документ |
| 5. Типы и шаблоны | `test_scenario_5_*`: у каждого типа свой заголовок и свой состав реквизитов; один документ в двух шаблонах даёт тот же текст и другое оформление |
| 6. Обработка ошибок | `test_scenario_6_*`: отказ обработчика — понятная ошибка 503 без следов стека, сервис жив, повтор ведёт себя одинаково, уже подготовленный документ по-прежнему скачивается |

## Что проверяется внутри DOCX

- файл открывается как обычный документ Word: целый архив, валидный XML, нет непринятых исправлений;
- текст лежит в абзацах и редактируется, картинок вместо текста нет;
- страница A4, поля, шрифт, кегль, межстрочный интервал и отступ после абзаца совпадают с правилами шаблона;
- выравнивание заголовка и основного текста, красная строка — по шаблону;
- шрифт объявлен и для латиницы, и для кириллицы, иначе Word подставит другой;
- порядок реквизитов совпадает с порядком блоков выбранного типа документа;
- заполненные реквизиты не оставляют меток `[Заполнить: …]`, пустые необязательные не занимают места;
- кавычки-ёлочки, тире, «ё» и знак номера доходят до файла без искажения;
- в свойствах файла нет постороннего автора.

## Найденные расхождения с эталоном кейса

Сверка автоматическая: `scripts/qa_report.py` сравнивает `/api/catalog` с
`examples/reference/case_reference.yaml`. Сейчас расхождений 11.

### Состав реквизитов

| Расхождение | Что сделать |
| --- | --- |
| «Служебная записка»: нет обязательного «Номер» (эталонный формат `47-СЗ`) | добавить поле `number` в `backend/app/doc_types/01_service_memo.yaml` |
| «Докладная записка»: нет обязательного «Номер» (формат `12-ДЗ`) | добавить поле `number` в `02_report_memo.yaml` |
| «Докладная записка» требует `organization`, которого нет в эталоне | сделать необязательным либо обосновать как расширение |
| «Информационная справка» требует `organization` и `purpose` — их нет в эталоне | по эталону обязательны только заголовок, дата, составитель, текст и подпись |
| Опциональных реквизитов эталона нет ни у одного типа | эталон даёт «Исполнитель» (ФИО и телефон) запискам и письму, «Адресат» — справке; в сервисе вместо этого «Приложение» у докладной записки и письма |

Эталон дополнительно разрешает автозаполнение двух реквизитов — даты текущей датой и
номера порядковым. Сейчас оба всегда запрашиваются у пользователя. Это не ошибка,
а нереализованная возможность: она заметно сокращает ручной ввод.

### Оформление шаблонов

| Расхождение | Эталон |
| --- | --- |
| «Классический»: колонтитулы не заданы | верхний — название организации, нижний — номер страницы, кегль 11 pt |
| «Компактный»: кегль 11 pt | 12 pt |
| «Компактный»: поля 25 мм сверху, справа и снизу | сверху 15, справа 20, снизу 15, слева 25 |
| «Компактный»: колонтитулы не заданы | нижний — название документа и дата, кегль 10 pt |
| «Компактный»: адресат и подпись — обычные абзацы | табличная шапка «Кому / От кого», подпись по центру |

Колонтитулы названы в критериях оценки прямо: сценарий 1 требует соответствия шаблону
«по полям, шрифту, интервалам, выравниванию, колонтитулам и расположению реквизитов».

Важно при исправлении кегля и полей «Компактного»: значения зафиксированы в
[test_documents.py:103](../backend/tests/test_documents.py#L103) и
[test_documents.py:105](../backend/tests/test_documents.py#L105) — их нужно поправить тем же
изменением, иначе проверки упадут. Тесты из `test_docx_conformance.py` править не придётся:
они берут ожидаемые значения из каталога сервиса, а не из копии.

## Ограничения проверок

Заглушка `stub` переносит текст дословно, поэтому на ней проверки сохранения фактов и запрета
на выдуманные значения проходят сами собой. Настоящую цену они имеют на реальной модели —
для этого есть `test_llm_scenarios.py`:

```bash
QA_LLM=1 python -X utf8 -m pytest tests/test_llm_scenarios.py -v
```

Набор пропускается, если не задан `QA_LLM=1`, если в ветке ещё нет режима `llm`
или если не указан `LLM_MODEL`. Он же — готовый приёмочный набор для ИИ-обработчика:
модель обязана переписать текст, сохранить все значения из `must_keep`, не добавить новых
чисел и не заполнить реквизиты из `not_in_draft`.

Браузерных автотестов интерфейса пока нет, внешний вид документа машиной не проверяется.
Это закрывают ручные проверки ниже.

## Ручные проверки

Внешний вид документа (открыть файлы из `qa_samples` в Word и LibreOffice):

- оба шаблона: поля, шрифт, интервалы, красная строка, положение адресата и подписи;
- длинный документ: переносы между страницами, отсутствие разорванных реквизитов;
- кириллица отображается тем же шрифтом, что и латиница;
- документ правится как обычный текст: абзац можно дописать и удалить.

Интерфейс:

- ширина 320 px: нет горизонтальной прокрутки, кнопки доступны;
- перезагрузка страницы восстанавливает черновик и введённые реквизиты;
- смена шаблона не отправляет повторный запрос на обработку;
- при ошибке обработки текст не пропадает и доступна повторная попытка;
- навигация с клавиатуры проходит все три шага.

## Чек-лист перед защитой

1. `python -X utf8 -m pytest -q` в каталоге `backend` — зелёный.
2. `backend/.venv/Scripts/python scripts/qa_report.py --out qa_samples` — черновиков с замечаниями 0.
3. Восемь образцов документов открыты в Word, вёрстка проверена.
4. Сценарии 1–6 пройдены руками через интерфейс, а не только тестами.
5. Отказ модели показан вживую: текст сохранён, ошибка понятна, повтор работает.
