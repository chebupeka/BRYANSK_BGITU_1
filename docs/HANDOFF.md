# Передача команде

Сначала всем запустить проект по README и пройти один путь до DOCX. Затем договориться об изменениях API через `schemas.py` и обновлять соответствующие типы в `frontend/src/types.ts` в том же изменении.

## Области работы для шести участников

| Участник | Начать с | Следующий результат |
| --- | --- | --- |
| 1 · API и инфраструктура | `backend/app/main.py`, `settings.py`, Compose | Кэш по черновику, профиль Ollama в Compose, стабильный API |
| 2 · ИИ и факты | `backend/app/processing.py`, `schemas.py` | Сделано: промпт, JSON-схема, сверка фактов, один повтор. Дальше: словесные числа и падежи, качество на длинных текстах |
| 3 · DOCX и конфигурации | `docx_generator.py`, `doc_types`, `templates` | Сверка с эталонами, реквизиты и оформление всех типов, визуальная проверка |
| 4 · Интерфейс | `frontend/src` | Уточнение реквизитов после извлечения, состояния реального ИИ, доступность |
| 5 · Проверки | `backend/tests`, `examples` | Сценарии 1–6, браузерные автотесты, длинные документы, сохранение смысла |
| 6 · Документация и демонстрация | `README.md`, `docs`, `examples` | Актуальные инструкции, демонстрационный сценарий и презентация до 7 минут |

Не требуется сначала строить микросервисы, базу данных, историю или корпоративные интеграции. Следующая цель — качественное исправление текста с сохранением фактов в уже работающем пути.

Режим `llm` подключается по разделу «Подключение Ollama» в README и по умолчанию выключен: проверки и демонстрация каркаса работают без установленной модели. Тесты адаптера используют расписанные ответы вместо живой модели, поэтому GitHub Actions Ollama не требуется.

## Проверка перед передачей

| Сценарий | Что проверить сейчас | Что ещё сделать для конкурсного MVP |
| --- | --- | --- |
| Полный путь | Вставить пример, заполнить поля, скачать редактируемый DOCX | Подключить проверенный ИИ |
| Орфография и стиль | В `stub` текст `examples/typos.txt` не меняется; в `llm` с запущенной Ollama ошибки исправлены, факты те же | Оценить качество на длинных документах |
| Недостающие реквизиты | Пустые обязательные поля получают метки; введённые значения попадают в DOCX | Автоматически извлекать подтверждённые поля из исходника |
| Факты и смысл | Даты, ФИО, сумма и условие точно сохраняются заглушкой | Сохранение после реального переформулирования, без новых фактов |
| Типы и оформления | Все 4 типа × 2 оформления; другой тип меняет набор полей и порядок | Сверить конфигурации с предоставленными эталонами |
| Отказ обработки | `unavailable` → ошибка; `stub` → повтор; данные остаются | Сетевые сбои, неверный JSON, ошибки фактчекинга реального провайдера |

Дополнительные ручные проверки интерфейса: пустой ввод блокирует переход; обновление страницы восстанавливает черновик и реквизиты; после возврата к другому типу его поля сохраняются; изменение реквизитов обновляет результат; смена только оформления не отправляет `/api/process`. Проверить ширину 320 px и клавиатурную навигацию.

Визуально открыть DOCX в Word и LibreOffice: проверить каждый из двух шаблонов, длинный текст на несколько страниц, поля, переносы, кириллицу, заголовок и отсутствие обрезанных реквизитов. Сравнить содержание файлов после смены оформления. Шрифты должны быть установлены на машине просмотра; заменяющий шрифт может изменить переносы.

### Проверка исходного каркаса

При подготовке каркаса прошли 22 теста backend, Ruff, `pip check`, TypeScript и production-сборка frontend. В браузере проверены скачивание обоих оформлений, сохранение текста и реквизитов после перезагрузки, отдельные реквизиты разных типов, отсутствие повторной обработки при смене оформления, ошибка 503 с повтором и отсутствие горизонтального переполнения на ширине 320 px. Интерфейс просмотрен на снимках desktop и mobile.

После исправления сетевого таймаута pip проверены реальная сборка и запуск Docker Compose: оба контейнера имеют статус healthy. `python scripts/check_docker.py` проверяет интерфейс, API, подготовку и скачивание обоих оформлений DOCX через nginx. Такая же проверка включена в GitHub Actions; frontend имеет healthcheck, чтобы проверка начиналась после готовности веб-сервера.

Структура и текст DOCX проверены тестами; визуальный рендер документов пока не выполнен из-за отсутствия доступного LibreOffice. Команде остаётся проверить внешний вид в офисном редакторе на своей машине.

## Порядок совместной работы

1. Создавать ветки от `main` под конкретную область или небольшую задачу.
2. В PR описывать изменение поведения и выполненные проверки.
3. При изменении API обновлять документацию, типы интерфейса и примеры.
4. Не коммитить `.env`, ключи API, реальные документы и локальные зависимости.
5. Перед объединением дождаться проверок backend и frontend.

Исходники постановки и критериев были предоставлены отдельно в папке `tasks` рабочего каталога; бинарные материалы не дублируются в кодовом репозитории. Краткий контекст сохранён рядом в `CONTEXT.md`.
