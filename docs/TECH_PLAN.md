## Задача 1. Рабочая обработка сразу после запуска

**Критерии:** раздел 5, сценарии 2 и 4 (0–3); раздел 4, «Документация и
воспроизводимость запуска» (0–3). Попутно — раздел 2, «Качество ИИ-обработки текста».

Сейчас `TEXT_PROCESSOR=stub` в [settings.py:16](../backend/app/settings.py:16),
[.env.example](../.env.example) и [compose.yaml](../compose.yaml).
[StubProcessor](../backend/app/processing.py:45) переносит строки дословно. Эксперт
выполняет `docker compose up --build` по README и получает документ, в котором
«Здрасьте! Нам надо купить три компа» осталось как есть. Критерий требует максимум
только тогда, когда эксперт проходит обязательные сценарии без обращения к команде.

Что сделать, по возрастанию трудозатрат — достаточно одного варианта:

1. Указать в `.env.example` доступный извне OpenAI-совместимый endpoint, который держит
   команда, и проверить его с чистой машины.
2. Профиль Compose, который сам поднимает Ollama и тянет модель при первом запуске
   (сейчас [профиль `ollama`](../compose.yaml) требует ручного `ollama pull`).
3. Детерминированный NLP-обработчик как значение по умолчанию: словарная правка
   орфографии и замена разговорных оборотов на деловые, без модели. Критерий прямо
   разрешает «сочетание ИИ и NLP-инструментов» и отдельно оговаривает, что сложность
   подхода сама по себе преимущества не даёт. Это переводит сценарии 2 и 4 из нуля в
   1.5–2 балла даже без сети.

**Проверка:** на машине без `.env`, без установленной Ollama и без ключей выполнить
`docker compose up --build`, вставить `examples/drafts/service_memo_02_colloquial.txt`
и получить DOCX с исправленным текстом. Пока этот проход не работает — задача не закрыта.

## Задача 2. Разбор реквизитов без двоеточия

**Критерии:** раздел 5, сценарий 3 (0–3); раздел 5, сценарии 2 и 4.

[LABEL_LINE](../backend/app/extraction.py:15) требует двоеточие или тире с пробелами.
В демонстрационном образце [samples.ts:21](../frontend/src/lib/samples.ts:21) строки
написаны без них: `Дата 12.03.2025`, `Номер 47-СЗ`, `Заголовок О закупке офисной техники`.
Проверено в браузере: из шести обязательных реквизитов заполняются два, а Тема, Дата,
Номер и Подписант уходят в документ метками `[Заполнить: …]`. Это первое, что видит
эксперт, нажав «Попробовать на примере».

Что сделать:

- разрешить метку без разделителя, когда первое слово строки входит в
  [FIELD_KEYWORDS](../backend/app/extraction.py:23), а остаток строки не пуст;
- добавить случай в [test_extraction.py](../backend/tests/test_extraction.py) на каждую
  форму записи: с двоеточием, с тире, без разделителя;
- проверить, что [body_lines](../backend/app/extraction.py:46) по-прежнему убирает такую
  строку из текста документа и она не дублируется в абзацах.

**Проверка:** все пять образцов из `samples.ts` на шаге 2 заполняют все реквизиты,
которые в них названы; корпус `examples/drafts` продолжает проходить
`test_drafts_corpus.py` без новых заполненных полей из `not_in_draft`.

## Задача 3. Автозаполнение даты и номера

**Критерии:** раздел 5, сценарий 3; раздел 2, «Работа с реквизитами и шаблонами».

Эталон кейса разрешает определять два реквизита автоматически — дату текущей датой и
номер порядковым. Это зафиксировано в [QA.md](QA.md) как нереализованная возможность:
сейчас оба всегда запрашиваются у пользователя. Критерий сценария 3 отдельно говорит,
какие значения «допустимо определять автоматически».

Что сделать:

- пометить реквизит в YAML типа флагом вида `autofill: today` / `autofill: sequence`
  и учесть его в [catalog.py](../backend/app/catalog.py);
- подставлять значение только в пустое поле и только на шаге 2, чтобы пользователь видел
  подстановку и мог её изменить — молчаливая подстановка при генерации нарушит требование
  «не подставляет вымышленное значение»;
- в интерфейсе отметить такое поле как заполненное автоматически.

**Проверка:** пустая Дата на шаге 2 показывает сегодняшнее число с пометкой источника;
введённое пользователем значение не перезаписывается; `missing_fields` на эти поля
больше не срабатывает.

## Задача 5. Длительные операции

**Критерии:** раздел 3, «Масштабируемость решения» (0–3).

Сейчас обработка синхронная: `/api/process` держит HTTP-соединение всё время работы
модели, а на локальной модели это до двух минут. Ограничение одновременных обработок
есть ([MAX_CONCURRENT_PROCESSES](../backend/app/main.py:54)), кэш и нарезка длинного
черновика есть, повторный вызов при смене оформления исключён. Критерий отдельно
называет «корректную работу с длительными операциями формирования документов».

Минимум: описать текущее поведение и его границы честно — таймауты, поведение при обрыве
соединения, почему выбран синхронный вызов. Полный вариант: идентификатор задачи и
опрос состояния, но это заметная переделка контракта и интерфейса; браться только если
задачи 1–4 закрыты.

## Задача 6. README под эксперта

**Критерии:** раздел 4, «Документация и воспроизводимость запуска» (0–3).

[README.md](../README.md) — 28 КБ, написан как записка для ролей 1–3 внутри команды.

окружения → как добавить тип документа и шаблон → известные ограничения. Внутреннюю
терминологию ролей убрать в [HANDOFF.md](HANDOFF.md).
